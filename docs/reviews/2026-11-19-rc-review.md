## 1. A later "blocked" must withdraw an earlier APPROVE

**RC:** a COMMENT doesn't cancel an APPROVE on GitHub, so a red CI re-run or a late P1 leaves the PR mergeable. Dismiss on any move away from approved, not only on a push.

**Our code:** already dismisses on any move away from `approved` ([scheduler.py](../../src/control-plane/doppel_control_plane/scheduler.py), `merge()`). The spec only mentions pushes, and no test covers approved → blocked on the same head.

**Fix:** say it in DSV-11; add the test.

**Decided (2026-11-20), built:** a requested person's reviewer is required, for 2 hours from when it was first queued on the current head; then the merger stops waiting for it (each reviewer has its own clock; a blocked or out-of-usage one counts the same). Its P0/P1s still block whenever they arrive, and withdraw an approval already given. `tick` re-runs the merger, so the clock running out needs no other event. The status comment says how long each person is waited for.

## 2. The merger must fail closed and keep Doppelwerk's guards

**RC:** `criticality.decide` refuses to approve when the review didn't read every changed file, when the diff was cut short, over the file ceiling, on drafts, on critical PRs, and below the repo's trust level. Partial reads are common (6 of 19 files, 1 of 11 this week). A required reviewer that failed, was skipped, or read only part of the PR must block. An empty check read as a pass once merged a PR without review.

**Our code:** a required reviewer that failed or was skipped leaves the merger on `waiting_reviews` forever: closed, but silent. Partial reads, truncated diffs, the file ceiling, drafts, critical PRs and trust aren't checked. "No CI result" is `waiting_ci`, which is safe.

**Fix:** a failed or skipped required reviewer is `blocked` ("repo-owner failed: a person has to review"); a slot records files reviewed against files changed; intake must never map zero checks to `success`.

**Decided (2026-11-20):** for the POC the merger approves on P0/P1 alone (plus required reviewers done, an app reviewer's stand-down, CI). Doppelwerk's other guards come later; the incomplete-read guard first, since RC saw it cause bad approvals.

## 3. A dead sign-in vs a usage limit

**RC:** Crew said "out of quota" for 12 hours when its keys had been refused, because it matched "billing" in the text. A 401/403 or a failed refresh should block with "reconnect Codex" and mark the credential expired; only a real usage-limit answer waits for the reset. Keep the provider's status, code and type.

**Our code:** the gateway already tells them apart by error type, not text (only `usage_limit_reached` records a reset). But a failed refresh or a second 401 just returns 503 to Codex; the scheduler isn't told, so the slot fails and retries on a dead credential.

**Done (2026-11-20):** after the one refresh-and-retry, a 401, a 403 or a failed refresh is a dead sign-in: the gateway tells the broker (`rejected`), which shows the payer `expired` and stops handing out the credential until they sign in again; Codex gets "reconnect Codex" (401 `credential_expired`), not a retry. Every provider error records its status, `code` and `type` on the slot (schema version 3). Only a 429 of type `usage_limit_reached` waits for a reset; a message that says "billing" changes nothing (tested). The scheduler blocks a payer without a working sign-in and says "Reconnect Codex" once on the PR.

## 4. Who may clear a blocking finding; matching across heads

**RC:** a person resolving or replying can clear a P0/P1 and lead to an approval with no new review, so a PR's author can clear their own blocker. Require someone other than the author, with write access, and don't count a bare reply for P0/P1. Loose matching across heads dropped findings in Doppelwerk until `seen_rounds`.

**Our code:** any disposition from anyone closes a finding. Only the latest verdict on the current head counts, so a P1 the model forgets to repeat disappears.

**Fix:** a P0/P1 is cleared only by a resolved thread from a non-author with write access (rule in control-plane core; intake supplies author and permission). Port Doppelwerk's `seen_rounds` / `still_open`: an unaddressed P0/P1 carries forward until fixed or cleared.

## 5. Capabilities visible across reviewers in one pod

**RC:** one reviewer spending another user's capability is the account sharing "who pays" forbids. A separate Unix user per reviewer run keeps each capability readable only by its own process.

**Our code:** spike 0a found the same; the spec lists it as a risk.

**Done (2026-11-20):** each reviewer run is `docker exec --user` its own user from a pool of 16 in the image, with the capability only in its process's environment (passed by name, never on a command line). The Docker test checks another reviewer user sees no capability in any `/proc/*/environ`, while the owning user does.

## 6. Summini runs production

**RC:** it hosts Doppelwerk and the security doppel. `doppeld` takes 16 GB; 10 to 12 pods at 2 GB is 20 to 24 GB more on 48 GB. A Mac hit 100% disk and its Docker VM went read-only. Hand-unsealing OpenBao stops reviews on every reboot.

**Our code:** per-head checkouts are cleaned up; mirrors aren't bounded.

**Fix (checkpoint 7):** hard CPU, memory and disk limits on the VM; a disk budget for mirrors and checkouts, with cleanup; `<data_dir>` on a backed-up volume (sign-ins are on disk only for now, so the OpenBao unseal question waits for the move to a secret manager).

## 7. Webhooks forwarded by the BFF

**RC:** the runtime writes to GitHub, so it should verify GitHub's signature itself, not trust the forward. Name which part holds the webhook secret.

**Fix (checkpoint 6):** the runtime holds the webhook secret and checks `X-Hub-Signature-256`; the BFF forwards the raw body and headers untouched.

## 8. Polling budget

**RC:** per-person searches across tenants will hit GitHub's search limit of about 30 a minute.

**Fix (checkpoint 6):** poll with repo listing endpoints (open PRs and their requested reviewers), not per-person searches, under a calls-per-hour budget per installation.
